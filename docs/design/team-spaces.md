# 团队空间（Team Spaces）设计

状态：草案，待评审。本文定义"空间"的概念、空间配置的存放与格式、分层锁定、多空间、凭据和安全边界，以及宿主需要补的能力和分阶段计划。插件体系本身见 [PLUGINS.md](../../PLUGINS.md)。

## 1. 目标与非目标

目标：

- 每个业务团队有自己的**空间**。同一空间的成员打开 Pi Desktop，看到的项目、仓库配置、插件、技能、模型网关、权限策略和开发流程都一样。
- 新成员加入空间后几分钟内可以开工：插件、规范和网关自动就位，仓库一键克隆。
- 规范的变更可审查、可追溯、可回滚。
- coding 之外的业务团队（例如财务）用同一个概念：一个没有代码仓库、装着业务插件的空间。
- 不新建服务器，不新建账户体系。身份和权限都来自内部 GitLab（企业版）。

非目标：

- 不用桌面端强制规范。人总能绕开桌面端直接用命令行，所以硬性规则由 GitLab 服务端执行（§8），桌面端负责引导和自动化。
- 不做空间之间的数据共享（会话、草稿等仍是个人的）。
- 第一版不做空间级的使用统计和集中审计上报。

## 2. 概念

**空间（Space）**：一个团队共享的工作环境定义，由一个**空间配置仓库**描述。空间不是文件夹，也不是 GitLab 群组。
_Avoid_：用"项目"或"群组"指代空间。

**空间配置仓库**：内部 GitLab 上的一个普通仓库，根目录有 `space.jsonc`，并打上 GitLab 主题（topic）`pi-space`。仓库可以放在任意群组下。

**空间成员**：对空间配置仓库有 Reporter 及以上权限的人。把某人加进这个仓库，就是让其加入空间；移出仓库就是退出空间。一个人可以属于多个空间。

**空间管理员**：对空间配置仓库有 Maintainer 及以上权限的人。修改空间配置要提 MR，由管理员合并。

**组织配置**：全公司共用的一层配置（§5），决定 GitLab 地址、可信证书、允许的插件来源和全公司的最低策略。

**当前空间**：用户此刻所在的空间。它决定启用哪些插件、哪个版本，以及使用哪些技能、网关和策略。切换空间不会结束正在后台运行的会话。

为什么不直接用 GitLab 群组：一个人会同时属于多个空间；一个团队的仓库分布在多个群组里。用配置仓库的成员来定义空间，与群组结构解耦，又不需要额外的成员管理系统。

## 3. 发现与同步

1. 用户用 GitLab 登录（GitLab OAuth 应用，§7）。
2. Pi Desktop 列出用户有权限的、带 `pi-space` 主题的仓库（GitLab API `GET /projects?topic=pi-space&membership=true`），作为可加入的空间。也可以手动填写空间配置仓库的地址。
3. 用户选择空间后，Pi Desktop 拉取配置仓库的默认分支，校验 `space.jsonc`，再按配置安装插件、同步技能、配置网关和策略。
4. 之后在应用启动时、切换空间时、手动点击"同步"时，以及每隔一段时间（默认 30 分钟）自动拉取一次。配置有变化时显示变更摘要；如果新增了插件权限或高风险项，先让用户确认再生效（§9）。
5. 拉取失败（离线、GitLab 不可达）时继续使用上次成功同步的版本，并在空间入口标出"未同步"。

空间配置仓库的内容按提交哈希缓存在 `<数据目录>/spaces/<空间 id>/<提交哈希>/`，生效的版本记录在偏好设置里，可以回退到上一个版本。

## 4. `space.jsonc` 格式

格式是 JSONC（允许注释），使用 zod 校验，并提供 JSON Schema，`$schema` 字段可以让编辑器给出补全和报错，做法与插件 manifest 相同。下面的示例展示各字段的含义：

```jsonc
{
  "$schema": "https://<内部地址>/pi-space.schema.json",
  "schemaVersion": 1,
  "id": "payment",                       // 空间 id，全局唯一
  "name": "支付团队",
  "description": "订单、支付与对账",

  // 空间里的仓库，可以来自任意群组
  "projects": [
    { "gitlab": "payment/order-service" },
    { "gitlab": "infra/shared-sdk", "optional": true }  // 默认不克隆
  ],
  "projectsRoot": "~/work/payment",       // 建议的本地克隆目录，个人可以改

  // 插件：来源是内部 GitLab，按 tag 锁定版本
  "plugins": [
    { "source": "gitlab:tools/pi-plugin-tapd", "ref": "v1.2.0", "locked": true },
    { "source": "gitlab:tools/pi-plugin-quality-gate", "ref": "v0.3.0", "locked": true },
    { "source": "gitlab:tools/pi-plugin-mr-flow", "ref": "v0.5.1" },
    // 插件设置可以由空间统一给出，locked 表示成员不能改
    { "source": "gitlab:payment/pi-plugin-recon", "ref": "v0.1.0",
      "settings": { "env": "staging" }, "lockedSettings": ["env"] }
  ],

  // 技能和 MCP 服务器，路径相对于空间配置仓库
  "skills": ["skills/"],
  "mcpServers": [],

  // 模型网关：只写地址和协议，密钥由每个人自己填（§7）
  "gateways": [
    { "id": "team-gw", "baseUrl": "https://ai-gw.payment.内网", "engines": ["pi", "claude", "codex"] }
  ],
  "models": {
    "default": { "engine": "pi", "gateway": "team-gw", "model": "deepseek-v4" },
    "allowedGateways": ["team-gw"]        // 不写就是不限制
  },

  // 权限策略
  "policy": {
    "defaultLevel": "ask",               // ask | auto | full：请求批准 / 帮我批准 / 完全访问
    "maxLevel": "auto",                  // 成员能选的最高档位
    "alwaysConfirm": ["git push --force*", "rm -rf *"],
    "deny": ["curl * | sh"]
  },

  // 开发流程：插件读取这些值，GitLab 推送规则也从这里生成（§8）
  "workflow": {
    "tapd": { "workspaceIds": ["12345678"] },
    "branch": "feature/{tapdId}-{slug}",
    "commit": "{type}: {summary} --story={tapdId}",
    "mrTemplate": "templates/mr.md",
    "reviewChecklist": "templates/review.md",
    "qualityGate": ["npm run lint", "npm test"]
  }
}
```

说明：

- `workflow` 不由宿主解释，而是作为空间级设置交给插件读取（新增 `pi.space.config()`，§10）。宿主只校验它是一个对象。这样以后的财务空间可以有自己的 `workflow` 内容，宿主不用改。
- 仓库自己的配置放在仓库里的 `.pi-desktop/`（技能、质量检查命令、审查清单），优先级低于空间锁定的项（§5）。

## 5. 分层与锁定

配置分四层，从上到下：

| 层 | 存放 | 谁能改 |
|---|---|---|
| 组织 | 组织配置仓库（地址在安装包中预置，或首次启动时填写一次） | 平台负责人 |
| 空间 | 空间配置仓库的 `space.jsonc` | 空间管理员（经 MR） |
| 仓库 | 仓库里的 `.pi-desktop/` | 仓库的维护者 |
| 个人 | 本机偏好设置 | 本人 |

规则：

- 下层可以覆盖上层**没有锁定**的值。上层锁定的值，下层的设置被忽略，界面上显示"由某某空间锁定"。
- 策略类的值只能收紧，不能放宽：`maxLevel` 取各层中最严的；`alwaysConfirm`、`deny` 取并集；`allowedGateways` 取交集。
- 组织层决定全公司的约束：GitLab 地址和 OAuth 应用 ID、自定义 CA 证书、TAPD 地址、**允许的插件来源**（例如只允许 `tools/*` 和各团队自己的群组），以及全公司的最低策略。

## 6. 多空间

- 活动栏顶部是空间切换器。每个空间有自己的项目列表和会话列表；个人偏好（主题、语言、快捷键）不随空间变化。
- 插件按空间启用。两个空间可以锁定同一个插件的不同版本，因此插件按 `<id>@<版本>` 并存安装，当前空间决定使用哪个版本。只有当前空间用到的版本会启动插件进程。
- 同一个仓库可以属于多个空间。从哪个空间打开它，就按哪个空间的配置运行；仓库自己的 `.pi-desktop/` 不受影响。
- 后台会话保持它启动时所在空间的配置，切换空间不会影响它。
- 不属于任何空间也可以使用 Pi Desktop，行为与现在一致（个人模式）。

## 7. 身份与凭据

所有凭据只保存在本机，用 `safeStorage` 加密，不写进任何仓库。

| 凭据 | 来源 | 用途 |
|---|---|---|
| GitLab | OAuth 登录（组织层配置 OAuth 应用）；也可以退回到个人访问令牌 | 发现空间、拉取配置和插件、代码审查（MR） |
| TAPD | 个人令牌，第一次使用 TAPD 插件时填写 | TAPD 插件 |
| 模型网关 | 每个空间的网关由成员自己填密钥，按 `空间 id + 网关 id` 保存 | Pi / Claude Code / Codex |

插件不能读到原始的 GitLab 令牌（与现有 forge 服务的做法一致）。TAPD 这类第三方令牌，通过新增的插件凭据接口 `pi.secrets` 管理（§10）：凭据按插件隔离，由宿主加密保存，填写界面也由宿主显示。

## 8. 引导与强制

| 规范 | 桌面端（引导与自动化） | GitLab 服务端（强制） |
|---|---|---|
| 分支命名 | 从 TAPD 单子开会话时自动建分支 | 推送规则：分支名正则 |
| 提交信息 | 自动生成并带上 TAPD 关联关键字 | 推送规则：提交信息正则 |
| MR 描述 | 按模板自动填写 | MR 描述模板（`.gitlab/merge_request_templates/`） |
| 质量检查 | 每轮结束时自动运行，失败结果交还 Agent 修复 | CI 流水线，加上"流水线通过才能合并" |
| 审查 | 用 Pi 审查时带上审查清单 | MR 审批规则、受保护分支 |

对应的正则和模板从 `space.jsonc` 的 `workflow` 生成。提供一个"导出 GitLab 规则"命令，输出推送规则的正则和模板文件，由管理员手动应用到 GitLab；第一版不自动修改 GitLab 设置。

## 9. 安全

- 空间配置仓库能决定往成员电脑上装什么插件，因此等同于在成员电脑上运行代码的权限。限制手段：
  - 组织层规定**允许的插件来源**，超出范围的插件拒绝安装，并在空间入口报错。
  - 空间插件的信任级别是新增的"空间托管"：免去安装确认，但仍然受权限网关约束，审批和审计规则不变。
  - 插件的新版本**新增权限**，或者空间新增了**高风险**插件时，同步会暂停这一项，每个成员都要确认一次。
  - 同步时用 Git 获取，并校验 tag 指向的提交没有变化；如果有人把 tag 改指向另一个提交，拒绝安装并提示。
- 空间配置不能放宽组织层的策略（§5）。
- 插件进程以用户的账户权限运行（PLUGINS.md §21）。这一点在空间场景下不变，所以允许的插件来源必须由组织层控制。

## 10. 宿主需要新增的能力

| 能力 | 说明 |
|---|---|
| GitLab 适配器 | `src/main/forge/` 新增 GitLab（API v4）：MR 列表与详情、文件 diff、评论、合并、流水线状态；界面用词跟着平台改为"合并请求" |
| 平台按地址配置 | `remote.ts` 目前只按域名写死识别 `github.com` 和 `gitee.com`，改为由组织层声明 `git.公司.com → gitlab` |
| 自定义 CA | Main 发出的请求信任组织层配置的 CA 证书，或使用系统证书库 |
| GitLab OAuth 登录 | 组织层配置 OAuth 应用 ID，使用 PKCE 授权码流程 |
| 空间服务 | 发现、拉取、校验、缓存、分层合并、锁定、回退；新增 `src/main/spaces/` |
| 插件按 tag 安装、多版本并存 | 现在的 Git 来源只做浅克隆，不支持指定 ref，并且一个 id 只能装一个版本 |
| 按空间启用插件 | 现在插件是全局开关 |
| 插件 API | `pi.space.current()`、`pi.space.config()`（只读，返回 `workflow` 和该插件的空间设置）、`pi.space.onDidChange`；`pi.secrets.get/set/delete`；`net.fetch`（域名限定在 manifest 声明和组织层白名单的交集内） |
| 生命周期钩子 | `pi.agent.onTurnEnd`（PLUGINS.md 中列为未实现），以及开始会话、提交前、创建 MR 前 |
| 空间切换器 | 活动栏入口，项目和会话按空间分组 |

## 11. 首批空间插件（都放在内部 GitLab 的 `tools/` 下）

- **TAPD**：在活动栏整页里看"我的需求、任务和缺陷"；从某张单子开会话（自动建分支，把单子描述带进对话）；完成后回写状态和评论；提交时带上关联关键字。
- **MR 流程**：在内置代码审查插件的基础上接入 GitLab MR：按模板生成描述、关联 TAPD、用审查清单审查、查看流水线状态。
- **质量闸门**：每轮结束时运行 `workflow.qualityGate` 和仓库自己的检查，失败时把结果交还 Agent。
- **空间管理**：只有管理员能看到。在界面上修改空间配置，结果以 MR 的形式提交到空间配置仓库。

## 12. 分阶段计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| S1 GitLab 底座 | GitLab 适配器、按地址配置平台、自定义 CA、OAuth 登录 | 内部 GitLab 仓库的 MR 能在代码审查页面查看、评论、合并（E2E 测试使用模拟的 GitLab API） |
| S2 空间核心 | `space.jsonc` 格式与 Schema、发现、同步、缓存与回退、分层锁定、空间切换器、项目一键克隆 | 两个测试空间锁定不同的策略和网关，切换后在新建的会话中生效；离线时使用缓存版本 |
| S3 空间插件分发 | 按 tag 安装、多版本并存、按空间启用、"空间托管"信任级别、新增权限时确认 | 两个空间锁定同一插件的不同版本，各自生效；tag 被改指向其他提交时拒绝安装 |
| S4 插件 API | `pi.space`、`pi.secrets`、`net.fetch`、`onTurnEnd` 等钩子 | 示例插件通过类型检查，E2E 覆盖授权与拒绝 |
| S5 首批插件 | TAPD、MR 流程、质量闸门 | 一个试点团队用一周：从 TAPD 单子开始，到 MR 合并结束 |
| S6 管理 | 空间管理插件、导出 GitLab 规则 | 在界面上修改配置后，在配置仓库里生成对应的 MR |

## 13. 待定问题

- 组织配置仓库的地址，是在打包时写进安装包，还是首次启动时填写？
- 插件新增权限需要每个成员确认，还是空间管理员确认一次就够？前者更安全，后者对 50 个人更省事。
- 空间同步是否需要"灰度"：例如配置仓库的 `canary` 分支只对部分成员生效。
- 需要确认 TAPD 个人令牌的权限范围，以及有哪些接口可以用于回写状态和评论。
- 空间级的使用统计和审计汇总，以后是否需要上报到一个内部服务（会引入服务端，这一版不做）。
